# 5. Как это устроено внутри

Обзор. Подробности каждого компонента — в [[docs/design/README|design]],
основания сквозных решений — в [[docs/decisions/README|decisions]].

## Форма

Один Go-модуль и один deployable. Границы внутри проходят по владельцам данных и
инвариантам, а не по техническим слоям, и защищаются пакетами и направлением
импортов. Межмодульный вызов остаётся обычным Go-вызовом; сеть внутри монолита
не используется.

Ядро пишется автономно и **в памяти**. События, хранение и прочая
инфраструктура реализуются обычными типами; внешние системы не подключаются,
пока в них нет нужды.

Разбор авторской прозы в структуру нормы — внешний слой. Ядро принимает норму
уже структурной.

## Компоненты

| Компонент | Владеет | Зависит от |
| --- | --- | --- |
| `period` | номер периода, интервалы, сравнение | — |
| `journal` | запись: actor, должность, версии, correlation ID | `period` |
| `deduction` | правила, сила, вытеснение, безопасность, оценка, трасса, встроенные предикаты | — |
| `llm-runtime` | роли, изоляция контекста, валидация выхода, бюджет, батч, запись и воспроизведение | — |
| `scenario` | данные мира: люди, должности, статусы, начальный корпус | — |
| `corpus` | документы, уровни, нормы, вид нормы, периоды принятия и вступления | `period` |
| `facts` | установленные факты, решения, занятие должностей, прошения | `period`, `journal` |
| `entitlement` | **единственный ответчик**: что применимо к случаю в периоде, с трассой | `corpus`, `facts`, `deduction` |
| `competence` | должности, ответственности, несовместимые пары, проверка «вправе ли» | `entitlement` |
| `impact` | разница состояний между двумя версиями корпуса | `entitlement` |
| `linter` | проверки корпуса из каталога провалов | `corpus`, `deduction`, `impact` |
| `case` | прошение, вопрос, установление факта, решение, intercessio, вступление в силу, исполнение | `competence`, `facts`, `entitlement` |
| `actors` | что участник видит и что может; знание как данные | `case`, `llm-runtime` |
| `turn` | три фазы, переход, сборка периода | `case`, `actors`, `impact`, `linter`, `journal` |
| `report` | отчёт периода | `journal`, `linter`, `impact` |
| `api` | контракт наружу | `turn`, `report` |
| `front` | граф власти, листание периодов, кликабельная трасса | `api` |
| `censor` | узурпация, сговор, конфликт интересов, дрейф практики | `journal` |
| `storage` | замена памяти реальным адаптером | `facts`, `journal` |

Критический путь: `deduction` → `corpus` + `facts` → `entitlement` → `case` →
`turn`. Всё остальное висит сбоку. `journal`, `llm-runtime` и `scenario` не
зависят ни от чего и могут делаться в любой момент. `linter`, `impact` и
`report` не блокируют игру вовсе — они улучшают её наблюдаемость.

## Четыре шва

Интерфейс заводится там, где подстановка действительно наблюдается, и больше
нигде. Пустые «порты на будущее» запрещены: они фиксируют неизвестные
абстракции и делают код церемониальным.

Таких мест ровно четыре:

1. **`entitlement`** — стратегия разрешения норм. Обязательство заменяемости
   живёт здесь и считается выполненным только при наличии теста, прогоняющего
   сценарий казуса на подменённой стратегии;
2. **`actors`** — детерминированная заглушка против LLM-участника;
3. **`llm-runtime`** — живой вызов против записанного выхода;
4. **`storage`** — память против реального адаптера.

## Как это проверяется

Основная масса поведения проверяется обычным `go test` без сети, контейнеров,
реальных часов и случайности. Это требует не максимального числа интерфейсов, а
явных входов, детерминированного ядра и контролируемых эффектов.

Три вещи, специфичные для этого проекта:

- **вычислитель проверяется синтетическими программами** с заранее известным
  выводом и заранее известной нестратифицируемостью — без обращения к
  предметной области вообще;
- **период воспроизводим:** повторный прогон на тех же входах даёт тот же
  результат. Участники-модели при этом играются записанными выходами;
- **тест заменяемости:** сценарий казуса проходит на подменённой стратегии
  разрешения норм. Без него первый шов фиктивен.

Живые вызовы модели проверяются отдельно, версионируемым набором случаев с
ожидаемыми структурными свойствами и adversarial-входами. Смена модели или
prompt проходит тот же набор.

## Порядок сборки

Девять вех, и порядок задан зависимостями, а не вкусом. Сначала работает вывод
на синтетических правилах; потом из корпуса и фактов выводится состояние мира;
потом появляются проверки корпуса и пересчёт затронутых; потом дело проходит
весь путь и партия становится играбельной без интерфейса и без моделей. Дальше
живые участники, порождение дел из правок закона, наблюдаемость снаружи,
аналитика и, последним, настоящее хранилище.

Критический путь — первая, вторая и четвёртая вехи. Проверки корпуса и отчёты
игру не блокируют, они делают её наблюдаемой.

Полный список с составом, демонстрациями и гейтами —
[[docs/design/milestones|design/milestones]].

## Напряжение, которое стоит держать в виду

Метацель проекта — инженерная поверхность AI-стороны: оркестрация ролей,
бюджет, бэкпрешер, частичный отказ, реплей. Ничего из этого нет на вехах
M1–M4: критический путь ведёт через вычислитель, то есть через упражнение по
логическому программированию.

Смягчение известно и дёшево: `llm-runtime`, `journal` и `scenario` ни от чего
не зависят, поэтому могут вестись параллельно с M1–M2, а не после M4. Стоит ли
двигать их вперёд и в каком объёме — открытый вопрос, см.
[[docs/open-questions|открытые вопросы]].

## Главный риск реализации

Разрастание `deduction`. Он пишется под фиксированную схему предикатов, без
парсера, без текстового синтаксиса и без оптимизаций, пока правил десятки.

Стоп-правило: **захотелось написать парсер языка норм — компонент окончен.**
