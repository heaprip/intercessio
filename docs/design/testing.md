# Проверка

Большинство поведения проверяется обычным `go test` без сети, контейнеров,
реальных часов и случайности. Это требует не максимального числа интерфейсов, а
явных входов, детерминированного ядра и контролируемых эффектов.

## Уровни

**Доменные тесты.** Инварианты, переходы состояния, порождённые факты.
Конкретные типы, никаких моков инфраструктуры.

**Сценарные тесты use case.** Вызывают публичный вход сценария и подставляют
маленькие реализации в памяти только фактически нужных зависимостей: часы,
источник идентификаторов, корпус, система записи, задача модели. Проверяют
результат, эффекты и последовательность значимых фактов, но не внутренние
вызовы.

**Контрактные тесты.** Один набор проверок применяется к заглушке и к реальному
адаптеру. Отвечают на вопрос, одинаково ли они понимают контракт, а не доступен
ли внешний сервис.

**Интеграционные.** Отображение, транзакции, сериализация, повтор и
идемпотентность. Требуют контейнеров, запускаются отдельно от быстрого цикла.

**Evals.** Версионируемый набор случаев с ожидаемыми структурными свойствами,
adversarial-входами, допустимыми вариациями и базовой линией. Смена модели или
prompt проходит тот же набор. Для обычных Go-тестов используется предопределённый
выход, а не живой вызов.

## Три проверки, специфичные для этого проекта

### Вычислитель — синтетическими программами

`deduction` проверяется без предметной области: программы с заранее известным
выводом, заранее известным неразрешённым конфликтом — два правила с
противоположными выводами и необъявленным порядком — и заранее известным
нарушением безопасности правил. Казус для этого не нужен и только замедлит цикл.

### Реплей периода

Повторный прогон того же периода на тех же входах даёт тот же результат.
Участники-модели играются записанными выходами. Это одновременно тест и
механика: без воспроизводимости нельзя предъявить игроку диагноз.

Если обработчик события должен быть повторяемым, сценарий обязан проверить
дублирующую доставку, устаревшую версию и частичный отказ. Порядок считается
гарантированным только там, где это явно записано в контракте.

### Тест заменяемости

Сценарий [[docs/design/casus/citizenship|казуса]] проходит на **подменённой
стратегии разрешения норм**. Без него первый шов фиктивен, а обязательство
заменяемости остаётся словами.

Это гейт вехи [[docs/design/stages/derived-state|derived-state]], а не пожелание.

## Контракт durable commit

Один набор контрактных тестов выполняется для реализации в памяти и для каждого
реального адаптера. Минимальная матрица: конфликт версий, неизвестный исход
после таймаута, падение после commit, дублирующая доставка, повтор, сверка
зависших намерений, порядок в пределах одного ключа.

Эмулятор провайдера не является доказательством его транзакционных гарантий.
Критические случаи запускаются против реального окружения перед принятием
адаптера.
