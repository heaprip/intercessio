# Реализация durable commit

Контракт задан решением
[[docs/decisions/durable-commit-is-a-semantic-contract|durable-commit-is-a-semantic-contract]].
Здесь — как он ложится на разные механизмы. Ничего из перечисленного не выбрано
окончательно.

## Форма плана

Иллюстративно, не готовый Go API — конкретный интерфейс появится вместе с
первым use case:

```go
type CommitPlan struct {
	CommitID        string
	StreamID        string
	ExpectedVersion uint64
	Events          []EventEnvelope
	Publications    []Publication
	Effects         []EffectIntent
	Timers          []TimerIntent
}
```

`Publication` — намерение интеграции с устойчивым ID и ordering key, а не
сообщение конкретного брокера. Адаптер выбирает сериализацию, очередь и способ
возобновления доставки.

Успешный commit не обещает, что HTTP-запрос уже выполнен. Он обещает, что
намерение его выполнить не потеряется. Обработчик эффекта допускает повтор,
использует ключ идемпотентности и сохраняет исход.

## Реализации без ложной одинаковости

| Среда | Возможная реализация одного контракта |
| --- | --- |
| В памяти | append и детерминированная очередь под одной критической секцией |
| YDB | обновления row tables и записи в topics в одной serializable-транзакции |
| AWS | транзакция DynamoDB сохраняет state/events и delivery batch; Streams запускает relay в SQS/EventBridge |
| SQL | state/events и delivery rows в одной транзакции; poller или CDC доставляет наружу |

Сильная нативная гарантия YDB не запрещается ради AWS, а AWS-адаптер не
притворяется физически атомарным с SQS. Оба удовлетворяют одному наблюдаемому
контракту, но не одной эксплуатационной модели.

Замечание, которое легко пропустить: DynamoDB Streams гарантирует порядок
изменений **одного item** — это не порядок нескольких событий одной транзакции.
Ordering key и представление батча требуют отдельного дизайна.

## Event sourcing

Остаётся выбором конкретного контекста, а не умолчанием. Вероятно полезен для
журнала решений и долгоживущих процессов, где нужны реконструкция во времени и
аудит. Не назначается справочникам, кэшам и техническим проекциям.

Event sourcing решает dual write только если сохранение события одновременно
создаёт надёжный лог подписки. Таблица событий и независимый брокер без
транзакции, changefeed или relay сохраняют прежний разрыв.

## Managed workflow

Yandex Workflows использует YaWL и JSON-состояние, AWS Step Functions — ASL и
собственное состояние исполнения. Общий широкий `WorkflowEngine` либо протечёт
семантикой вендора, либо станет собственным DSL с компилятором.

Переносимый слой — детерминированный бизнес-переход и минимальные возможности:
сигналы, таймеры, эффекты, lease. Managed-движок может быть runner, если
каноническое состояние остаётся в Intercessio.

## Авторизация

OpenFGA экспортирует интерфейс хранилища, и собственный YDB-адаптер можно
подключить без форка ядра, но потребуется свой composition root: штатная
конфигурация знает только память, PostgreSQL, MySQL и SQLite.

Работа адаптера включает не только CRUD над кортежами: обратные чтения,
пагинацию, модели авторизации, assertions, changelog, транзакции и семантику
итераторов. Наличие своего хранилища **не** делает доменный commit и вызов
OpenFGA одной транзакцией; кортежи вероятно будут проекцией доменных фактов, а
критичный по безопасности отзыв прав требует отдельного дизайна согласованности.

Ничего из этого не нужно до вехи M9.

## Перепроверить перед спайком

- версии и ограничения YDB table/topic transaction SDK для Go;
- актуальный контракт хранилища выбранной версии OpenFGA;
- реальные лимиты размера транзакции, порядка и задержки выбранного провайдера.
