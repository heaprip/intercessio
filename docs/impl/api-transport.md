# Транспорт наружу

Решение — [[docs/decisions/proto-first-external-api|proto-first-external-api]],
и оно помечено как требующее пересмотра: принималось под внешних интеграторов, а
у игры один потребитель и собственный фронт.

Нужное на вехе [[docs/design/stages/external-view|external-view]], не раньше. До появления первой `.proto` пустой pipeline
генерации не заводится.

## Из одной схемы

Buf управляет зависимостями, lint, breaking checks и закреплённой по версиям
генерацией. Из одного контракта получаются Go-типы protobuf и grpc, серверные
stubs, gRPC-Gateway handlers для HTTP/JSON и OpenAPI artifact.

Каждый публичный HTTP-endpoint получает явную `google.api.http` annotation.
Сгенерированный REST не считается автоматически хорошим REST: пути, методы,
коды, идемпотентность и длительные операции проектируются вручную.

## Направление зависимостей

```text
HTTP/JSON или gRPC запрос
        -> сгенерированный transport-адаптер
        -> команда или запрос application
        -> доменное поведение
```

Application и домен не импортируют сгенерированные пакеты. Отображение явное,
потому что внешний контракт и внутренняя модель имеют разные причины меняться.

Модули монолита не вызывают друг друга через loopback HTTP/gRPC.

## Общая политика, разные middleware

Прямая in-process регистрация gRPC-Gateway удобна для unary serverless HTTP, но
**обходит gRPC-интерсепторы**. Поэтому:

- transport middleware извлекает credentials, заголовки, трассировку, request ID;
- application policy выполняет авторизацию, валидацию и идемпотентность;
- домен повторно защищает собственные инварианты;
- отображение ошибок в HTTP и gRPC — обязанность адаптеров.

Наличие gRPC-интерсептора не доказывает, что тот же контроль выполнен для REST.

## Развёртывание

Рабочая гипотеза, не выбор провайдера: Cloud Functions получает HTTP как JSON
event envelope и поэтому плохо подходит для синхронного API-сервера; Serverless
Containers обслуживают REST/JSON; Functions исполняют асинхронных потребителей;
native gRPC включается только там, где есть документированный HTTP/2 ingress.

## Отдельные контракты

Потоковый вывод модели, события прогресса периода, передача файлов и webhooks не
нужно насильно пропускать через unary JSON. Для них допускаются отдельные
SSE/WebSocket или message-контракты — после появления сценария и отдельного
решения.

Для игрового фронта это, вероятно, и есть основной случай: отчёт периода и
трасса вывода плохо ложатся в ресурсно-ориентированный REST.

## Перепроверить перед спайком

- стабильность генератора OpenAPI 3 у gRPC-Gateway (стабильный ориентирован на
  v2);
- наличие native gRPC ingress у выбранного serverless-хоста.
