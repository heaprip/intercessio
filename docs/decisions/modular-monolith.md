# Начать с модульного Go-монолита

Status: Accepted  
Proposed by: не подтверждено — см. [[docs/open-questions|открытые вопросы]]  
Accepted by: author  
Зависит от: —  
Заменяет: —

## Context

Система новая, предметные границы еще исследуются, а поведение должно легко
симулироваться нативными Go-тестами. Распределенное развертывание добавит сетевые
отказы и преждевременно зафиксирует неизвестные контракты.

## Decision drivers

- скорость изменения модели;
- атомарность важных инвариантов;
- локальная воспроизводимость;
- возможность выделить модуль позже по фактической нагрузке или ownership.

## Considered options

1. Модульный монолит.
2. Набор сервисов с брокером с первого дня.
3. Неструктурированный монолит с техническими слоями.

## Decision

Intercessio начинается одним Go module и deployable. Внутри границы строятся по
cohesive capability/bounded context и защищаются Go packages и направлением
импортов. Межмодульный вызов остается локальным, если нет отдельной причины для
асинхронности.

## Consequences

### Positive

- быстрые тесты и рефакторинг;
- меньше operational complexity;
- транзакционные границы можно обнаружить до распределения.

### Negative / trade-offs

- границы придется дисциплинированно защищать;
- независимое масштабирование и развертывание модулей отсутствуют;
- неосторожный shared database способен скрыто связать модули.

## Validation and re-evaluation trigger

Пересмотреть при доказанной потребности в независимом deployment, конфликтующем
масштабировании, разных reliability/security boundaries или самостоятельном
владении модулем командой. Размер кода сам по себе не является триггером.
