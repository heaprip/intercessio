# Разделить проектную память и проверять документацию как код

## Context

Проект разрабатывается одним автором совместно с AI-помощниками. Нужна память
между сессиями, но автоматически сгенерированное описание легко становится
убедительным и неверным. Одновременно требуется сохранить основания решений и
не забывать, когда они перестали действовать.

## Decision drivers

- один источник истины для каждого класса знания;
- совместимость с разными агентами и IDE;
- видимая эволюция решения без переписывания истории;
- автоматизация проверяемой механики без генерации неподтвержденного смысла;
- низкая стоимость поддержки на раннем этапе.

## Considered options

1. Tool-neutral `.agents/memory` + `docs` + ADR + локальные хуки и CI.
2. Хранить все в memory конкретного agent tool, например Serena.
3. Автоматически перегенерировать архитектурные документы из кода с помощью LLM.
4. Вести документы вручную без triggers.

## Decision

Выбран вариант 1:

- `.agents/memory` хранит только короткий актуальный snapshot;
- `docs` хранит продуктовый контекст, язык и архитектурные ограничения;
- принятые решения существуют как immutable ADR и заменяются новым ADR;
- [[AGENTS|AGENTS.md]] задает семантический change protocol;
- Lefthook локально и будущая CI запускают одинаковые repository scripts;
- внешние agent tools могут читать эту память, но не создают конкурирующий
  canonical store.

Автоматическая генерация допустима для производных артефактов из формальной
схемы. Текст, объясняющий «почему», меняется только как reviewable diff.

## Consequences

### Positive

- смена AI-клиента не уничтожает контекст;
- краткосрочная память не раздувает durable documentation;
- история причин сохраняется;
- hook и CI дают быстрый feedback.

### Negative / trade-offs

- смысловую актуальность все равно проверяет человек;
- часть данных приходится сознательно классифицировать;
- agent-specific memory может потребовать отключения или настройки;
- предупреждения об impact не доказывают отсутствие documentation drift.

## Validation and re-evaluation trigger

Через первые 20 существенных изменений проверить: были ли пропущены обновления,
стали ли hooks шумными и сколько раз помощники создавали противоречащие записи.
Пересмотреть при появлении нескольких постоянных авторов, отдельного docs portal
или зрелого надежного semantic drift detector.
