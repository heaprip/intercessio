# Стратегия тестирования

Статус: Draft  

## Цель

Большинство поведения должно проверяться обычным `go test` без сети, контейнера,
реальных часов и случайности. Это требует не максимального числа интерфейсов, а
явных входов, детерминированного ядра и контролируемых эффектов.

## Уровни

### Domain tests

Проверяют инварианты, переходы состояния, value objects и порожденные доменные
события. Используют конкретные типы. Никаких mocks инфраструктуры.

### Use-case scenario tests

Вызывают публичный вход сценария и подставляют маленькие in-memory реализации
только фактически нужных портов: clock, ID source, policy data, system of record,
LLM task. Проверяют результат, эффекты и последовательность значимых фактов, но
не внутренние вызовы.

### Contract tests

Один набор проверок применяется к fake и реальному адаптеру. Он отвечает на
вопрос, одинаково ли они понимают контракт, а не доступен ли внешний сервис.

### Integration tests

Проверяют mapping, транзакции, serialization, retry/idempotency и реальные
границы. Они могут требовать контейнеров и запускаются отдельно от быстрого
цикла.

### End-to-end tests

Немного критических путей проверяют wiring и развертывание. Они не должны
дублировать всю доменную матрицу.

### LLM evals

Это не только unit tests. Нужен версионируемый набор случаев с ожидаемыми
структурированными свойствами, adversarial inputs, допустимыми вариациями,
стоимостью ошибок и baseline. Смена модели или prompt проходит тот же eval gate.
Для обычных Go-тестов используется предопределенный fake output, а не live API.

## Симуляция событий

Сценарный harness принимает команду, начальные факты и контролируемые зависимости,
затем возвращает новые факты и запрошенные эффекты. Он не эмулирует Kafka или
таймеры брокера. Отдельные integration tests проверят transport semantics, если
они появятся.

Если обработчик события должен быть повторяемым, сценарий обязан проверить
duplicate delivery, stale version и partial failure. Порядок считается
гарантированным только там, где это явно записано в контракте.

## Durable commit contract

Один набор contract tests должен выполняться для in-memory и каждого реального
adapter из ADR-0006. Минимальная матрица включает version conflict, неизвестный
outcome после timeout, crash после commit, duplicate delivery, retry,
reconciliation и порядок в пределах ordering key.

Эмулятор provider не является доказательством его транзакционных гарантий.
Критические integration cases запускаются и против реального YDB/AWS test
environment перед принятием adapter.

## Transport parity

HTTP/JSON и gRPC adapters проверяют один набор application scenarios. Отдельные
contract tests фиксируют различия transport: error mapping, headers/metadata,
JSON encoding, pagination и отсутствие HTTP binding у внутренних RPC.
