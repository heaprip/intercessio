# Документация Intercessio

Документация — часть изменения. Она не обязана пересказывать код, но обязана
сохранять причины, язык и границы, которые из кода восстановить нельзя.

## Карта

- `product/vision.md` — зачем существует система и где заканчиваются ее
  полномочия;
- `domain/glossary.md` — ubiquitous language и запрещенные двусмысленности;
- `domain/context-map.md` — гипотезы о bounded contexts и их отношениях;
- `architecture/principles.md` — архитектурные ограничения;
- `architecture/testing.md` — уровни проверки и симуляция событий;
- `architecture/llm-boundary.md` — роль LLM, риски и контроль;
- `architecture/durable-execution.md` — канонический commit, эффекты и workflow;
- `architecture/api-boundary.md` — внешний REST/gRPC transport contract;
- `proposals/` — черновики помощников со статусом `НЕ ПРИНЯТО`; ничто отсюда
  не является основанием для кода, пока автор не перенес это сам;
- `decisions/` — история принятых и отмененных решений;
- `tooling/automation.md` — хуки, agent tooling и критерии их подключения;
- `research/` — датированные исследования, не являющиеся решениями.

Оперативный снимок лежит в `.agents/memory/`; он должен быть коротким и не
дублировать эти документы.

## Протокол актуализации

Для каждого изменения автор или помощник сначала определяет, что изменилось, а
затем в том же change set обновляет соответствующий источник:

| Изменение | Обязательное обновление |
| --- | --- |
| Цель, пользователь или scope | `product/vision.md` |
| Термин, бизнес-правило, инвариант | glossary и исполняемый тест/пример |
| Владелец данных или граница capability | context map |
| Сквозное, дорого обратимое решение | новый ADR |
| Замена принятого решения | новый ADR + `Superseded` у старого |
| Новый AI-риск или способ контроля | `llm-boundary.md` и eval/test plan |
| Активная задача или следующий шаг | `.agents/memory/current.md` |
| Не принятое предположение | `.agents/memory/open-questions.md` |

Помощник пишет только в `proposals/`. Перенос в `docs/` и присвоение ADR
статуса `Accepted` выполняет автор.

ADR не редактируют задним числом ради нового положения дел. Допустимы только
опечатки, уточнения ссылок и смена статуса. Новая логика оформляется новым ADR,
который указывает, что он заменяет.

## Что здесь означает «автообновление»

AI-помощники обязаны выполнять матрицу выше согласно `AGENTS.md`. Скрипт
`scripts/check-docs.sh` проверяет наличие ключевых файлов, даты и допустимые
статусы ADR. `scripts/check-doc-impact.sh` анализирует staged changes и отличает
жесткие механические ошибки от смысловых напоминаний. Оба подключены в
`lefthook.yml`; тот же набор команд должен выполняться в будущей CI-системе.

Скрипт намеренно не переписывает смысл документов: семантическое автообновление
создает правдоподобную, но не подтвержденную историю. Изменение документации
проходит то же ревью, что и код.

## Напоминание автору

Перед крупным решением ответить письменно:

1. Какой наблюдаемый сценарий или риск заставляет нас решать это сейчас?
2. Какие варианты рассмотрены, включая «ничего пока не делать»?
3. Какое допущение делает решение верным?
4. Каким тестом, метрикой или событием мы поймем, что допущение перестало быть
   верным?
5. Можно ли решение отложить до первого фактического ограничения?

Если основание эволюционно изменилось, не защищать старый ADR: заменить его.
